# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Проект русскоязычный целиком: README, промпты, докстринги, комментарии, сообщения
коммитов и общение с владельцем — по-русски. Пиши на русском **всегда**: в любой
сессии, в любом ответе, включая промпты агентам и их отчёты.

**Очередь задач — в [NEXT.md](NEXT.md).** Там лежат готовые промпты для следующих
сессий: сделанное вычёркиваем тем же коммитом, что и правку, всплывшее дописываем.
Кончились задачи — говорим об этом владельцу прямо, а не придумываем себе новые. Смысл файла — не платить
второй раз за разбор одного и того же контекста, поэтому промпт пишется
самодостаточным: путь, файлы, что проверить, чем закончить. Крупную задачу
отдавай агенту, а не тяни в основную сессию.

## Что это

**ПЛЁНКА** — автономный музыкальный канал в Telegram (`@plenka_fm`) с голосом владельца
и зеркалом во ВКонтакте. Сервера нет: всё крутится
на GitHub Actions, а состояние — обычные JSON-файлы в репозитории, поэтому git
работает бесплатной базой с историей и откатом. Подробности продукта — в
[README.md](README.md), план продвижения — в [GROWTH.md](GROWTH.md).

## Команды

Виртуальное окружение уже собрано, все модули запускаются как пакеты:

```bash
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m src.<модуль> [флаги]
```

Тестов и линтеров в проекте нет — папка `tests/` пуста, конфигов ruff/pytest нет.
Проверка изменений идёт «сухими» прогонами, они есть почти у каждого модуля
и намеренно ничего не пишут и не тратят токенов:

## Архитектура

### Конвейер

Три независимых шага, связанных только файлами состояния:

1. **[src/collect.py](src/collect.py)** — раз в 6 часов обходит iTunes, Deezer,
   YouTube, RSS и Telegram-каналы изданий (`src/sources/`), складывает находки
   в `data/inbox.jsonl`. Релизы ищутся по `data/artists.json`, а релиз, записанный
   на другого артиста, — по названию в кавычках из новости издания о своём
   артисте (`collect.releases_from_news`, только точное совпадение в Deezer). База
   пополняется и сокращается сама: раз в сутки `src/newcomers.py` добавляет
   уровнем `auto` тех, кого за две недели назвали два издания, одно из них —
   рэп-пресса, а iTunes знает под этим именем рэпера; полгода тишины выводит
   их из сбора, год — из базы. Собранных руками это не касается. Инфоповоды русской сцены берутся только из Telegram:
   RSS по ней вымер целиком (`data/feeds.json`), и веб-превью `t.me/s/<канал>` —
   единственный путь, не требующий ни ключа, ни чужого токена.
   Отпечатки виденного — в `data/seen.json`.
2. **[src/compose.py](src/compose.py)** — раз в сутки превращает сырьё из inbox
   в готовые посты `content/queue/*.json`. Батч асинхронный намеренно: один запуск
   `--submit` отправляет задание, следующий `--fetch` забирает — Actions не должен
   часами ждать ответа.
   Очередь намеренно вечнозелёная: рубрики с нулевым весом в `config.RUBRICS`
   (ИНФОПОВОД, ЛЕГЕНДА) в неё не пишутся — пост, привязанный ко дню, к своей
   очереди протухнет.
3. **[src/publish.py](src/publish.py)** — что и когда выходит; выпускает
   дежурство (`moderate.publish_shift`, проверка раз в 10 минут). Обычный пост —
   самый ранний файл очереди, в часы `config.PUBLISH_HOURS_MSK` (10, 19):
   пропущенный час наверстывается, ночью (23–9 МСК) не выходит (`publish.due`).
   Посты о релизах (`RELEASE_RUBRICS`) идут мимо слотов, не чаще раза
   в час (`publish.release_due`), через 2 часа после написания или сразу с треком
   владельца; старше суток от выхода они убираются, больше трёх за день
   (`config.RELEASE_PER_DAY`, самые весомые) не выходят, ночью — без звука,
   и каждый занимает обычный слот. Вместе со срочной новостью это три поста
   в обычный день и до пяти в пятницу (владелец 22.09.2026: семь в сутки
   и 14 в пятницу подписчик не успевал прочесть). **Крона у выхода нет намеренно**: ежечасный занимал
   общую группу `state-write`, где GitHub держит один ожидающий запуск, и вытеснял
   сбор новинок и срочные новости, а из четырёх обычных GitHub 13.09.2026 создавал
   один-два с опозданием на 3–5 часов. `publish.yml` остался ручным. Опубликованное
   уходит в `content/archive/` и `data/posted.json`.

Сниппет — кусок неизданного трека, который артист выложил сам, — идёт путём
срочной новости: своей рубрики у него нет, это тот же ИНФОПОВОД с меткой
`snippet` (ставит `collect` по данным, несёт `compose.save_post`). Отдельным его
делает только звук: сам кусок ложится под пост первым комментарием
(`comments.seed` → `telegram_web.preview_video`). Ссылку на файл Telegram отдаёт
с временным ключом, поэтому файл качается в момент отправки, а не при сборе, и заливается
ботом — по ссылке Telegram его не забирает;
большого ролика превью не отдаёт вовсе («Media is too big»), а бот чужой канал
не читает — такой ролик дежурство качает входом в аккаунт владельца
(`telegram_web.account_video`, ключи `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`,
`TELEGRAM_SESSION`) и заливает ботом. Не достаётся ни так, ни так — `urgent.run`
пропускает сниппет до модели: пост «показал сниппет» без самого сниппета пуст.
Ключ входа не открывать одновременно с двух машин: Telegram гасит его насовсем,
поэтому в аккаунт ходит только дежурство. Как звучит
сниппет, модель писать не вправе: она его не слышала, и `quality.py` по метке
это ловит.

Сбоку от конвейера: **[src/urgent.py](src/urgent.py)** (срочные новости: раз в день, в 14 МСК,
пишет пост по свежему инфоповоду в `content/urgent/` и сразу выпускает в канал;
заход запускает дежурство (`urgent.shift` → `urgent.yml`), крона нет по той же
причине, что у выхода постов; новость о своём артисте (score от 90) идёт раньше лент Telegram; в общую очередь срочные посты не попадают и через двое суток
без решения удаляются; после каждого сбора, здесь и в collect.yml, `compose --fresh`
пишет по посту на свежий релиз — РЕЛИЗ или ВЕРДИКТ, а `--ask-tracks` просит трек), **[src/service.py](src/service.py)** (ПРОЯВКА — разборы вкуса
в личке бота; ссылку на трек и «Артист — Трек» разбирает поиском отбора; 🔔 СЛЕЖУ — вести
о релизах и, по городу, о концертах в городе подписчика из Яндекс Афиши, `src/sources/afisha.py`),
**[src/svedenie.py](src/svedenie.py)** (СВЕДЕНИЕ: человек кидает ссылку на свои
лайки в Яндекс Музыке, бот отвечает «ты на N% <артист>» и карточкой для сторис.
Процент — доля лайков, где играет сам артист или его круг (`similarArtists`):
чужие лайки Яндекс не отдаёт никому, в том числе лайки артиста, и говорить
«залезли в его лайки» нельзя. Есть у артиста свой плейлист — второй строкой
совпадение с ним. Нет Яндекса или список закрыт — человек пишет 5–20 артистов
ответом на INTRO (метка `INTRO_MARK`: без ответа список ушёл бы в ПРОЯВКУ),
и счёт тот же: каждый названный идёт в снимок «треком» с одним исполнителем.
Яндекс называет только INTRO — в меню, кнопках и описании бота площадки нет.
Под ответом «👥 Сравнить с другом» — «поделиться» с личной ссылкой `?start=sv_<код>`:
код случайный, лежит в снимке, в `bot_sources.json` — одна метка `sv`; код друга ждёт
в его записи хранилища (`invite`), а не в памяти смены. Процент вдвоём — общие исполнители
к меньшему из двух множеств, у двух списков лайков ещё общие треки; итог и карточка
«вы совпали на N%» — обоим, имя друга не хранится. Адрес на карточках СВЕДЕНИЯ —
`config.BOT_HANDLE`, не канал: кто увидел её в сторис, считает свой процент у бота.
Снимок фонотеки — данные о человеке: только `config.PRIVATE`,
30 дней, три разбора в сутки. Запросы идут через функцию Яндекс Облака
(`cloud/yandex_music_proxy.py`): с адресов GitHub Яндекс отвечает 451),
**[src/skleyka.py](src/skleyka.py)** (СКЛЕЙКА: вокал и бит — в готовый трек, только ffmpeg; `/skleyka` —
выбор кнопкой «вокал + бит» или «по дорожкам», бот просит дорожки по шагам, роль файла — шаг, стиль — до склейки;
файлы при открытой заявке — дорожки, а не трек в ОТБОР (`skleyka.wants`, раньше отбора в `moderate.process`);
склеивает отдельный процесс `--job`, по одной, очередь двигает `skleyka.tick` на каждом круге дежурства;
файлы больше 20 МБ и WAV больше 50 МБ — служебным входом бота по MTProto (`telegram.service_login`,
секрет `TELEGRAM_BOT_SESSION`, открывать только в дежурстве); заявки с chat_id — в `config.SKLEYKA_FILE`),
**[src/otbor.py](src/otbor.py)** (ОТБОР, главная функция бота: артист присылает свой трек
ссылкой, «Артист — Трек» или файлом, проверки без владельца — подписка, трек в неделю,
артист не известен (`data/artists.json` и `config.OTBOR_MAX_FANS` на Deezer), трек выложен,
1–8 минут; заявки с chat_id — в приватном хранилище (`config.OTBOR_FILE`), пост шаблоном
без модели выпускает дежурство раз в день днём, трек — первым комментарием, артисту —
ссылка на пост), **[src/moderate.py](src/moderate.py)** (единственный поллер),
**[src/quiz.py](src/quiz.py)** (СЛЕПАЯ ПРОСЛУШКА: отрывок в канал, неанонимная
викторина — в комментарии, её вешает дежурство по пересылке; угадавшим назавтра
метка «знаток: …» в чате, список угадавших — в приватном хранилище),
**[src/stories.py](src/stories.py)**,
**[src/clips.py](src/clips.py)** (три формата: разбор связи из `lineage.json`,
`--facts` — факты про артиста из `facts.json`, `--news` — свежая новость
прямо из `inbox.jsonl`, строки к ней пишет модель по `llm.CLIP_SCHEMA`), **[src/host.py](src/host.py)**
(закадровый голос клипов),
**[src/reels.py](src/reels.py)** (ролики с живым голосом владельца: сценарий из ветки `claude/reels-*` приходит в личку по фразам, голосовые в ответ собираются в ролик с превью и текстом для заливки, картинки ответом на фразу встают вместо её кадров (подпись к фото — комментарий для Claude в `pics/*.txt`), сборку по ним запускает «собери»: под голосом бит из поля `music` или любимый владельца, кадры каждые 2–3 секунды, видео-мемы с GIPHY и фото событий из источников, субтитры по `say` (или `subtitle` с цифрами) ставятся сами, поэтому ярлыков `text`/`label` в кадре нет (`reels.burn`; метки у картинок: `.top` — субтитр наверх, `.nosub` — без субтитра, `.at` — секунда начала); метка Telegram с `config.CHANNEL_HANDLE` в левом верхнем углу и плашка с крутящимся аватаром канала и адресом в конце, рядом `reel-<id>-tiktok.mp4` без метки и без концовки (кончается с последней строкой, звук гаснет), `reel-<id>-vk.mp4` — адрес канала без значка Telegram, и `reel-<id>-channel.mp4` — вид TikTok-версии, но с битом; у трёх площадок бита нет — трендовый звук владелец добавляет при загрузке из библиотеки площадки (21.09.2026: вшитый тренд площадка трендом не считает, а YouTube ловит чужую фонограмму), звуки зала и отрывки треков остаются (поле `overlay`), фон зала на весь ролик — поле `room`, мимо сайдчейна; голос — мягкая дикторская цепочка, отзвук и дилей своими шинами, по трети от 10% и 7% (`reels.studio`, владелец 21.09.2026); бот шлёт все четыре; под канальной версией кнопка «📺 В канал» (`reels.to_channel`, ловит дежурство): ролик выходит через `publish.to_channel` по file_id нажатого сообщения, мимо слотов и без ВКонтакте, один раз — отметка `content/archive/reel-<id>.json`; субтитры, метка и концовка — в безопасной зоне `reels.SAFE_*`, снятой с записи экрана Shorts; бриф — `prompts/reels.md`, доводка ролика по картинкам и комментариям владельца — по `prompts/reels-edit.md`),
**[src/review.py](src/review.py)** (автопилот точности: облачный Claude по подписке каждые 2 часа сверяет новые посты с данными и пушит правки в ветку `claude/review-*`, `review.yml` применяет их к очереди; бриф — `prompts/review.md`, владельцу ничего не пишет),
**[src/health.py](src/health.py)** (сторож, пишет в личку только когда
что-то сломалось; молчаливый уход на запасной генератор — тоже поломка:
`llm._generate` отмечает в `data/llm.jsonl`, кто писал, и запасной больше
чем в половине текстов за сутки — строка владельцу).

### Ключевые узлы

- **[src/config.py](src/config.py)** — единственная точка правды: пути, секреты,
  лимиты, расписание и `RUBRICS` с весами. Меняешь поведение канала — почти всегда
  здесь. Пути к данным берутся отсюда, не собирай их вручную.
- **[src/state.py](src/state.py)** — всё чтение и запись состояния. `read_json`
  при битом файле переименовывает его в `.broken` и возвращает пустое состояние:
  один испорченный JSON не должен ронять запуск.
- **[src/llm.py](src/llm.py)** — генератор за фасадом. `LLM_PROVIDER` выбирает
  провайдера из `src/providers/` (gemini — основной с 20.09.2026, gigachat, anthropic),
  `LLM_FALLBACK` — запасного. **Фоллбек поднимается только на технических отказах**
  (кончились деньги, сеть, сервис); осознанный `skip` модели — это решение, а не
  поломка. Ответ жёстко ограничен `POST_SCHEMA`, свободный текст не разбирается.
  Голос канала уходит в system с `cache_control: ephemeral`.
- **[src/quality.py](src/quality.py)** — грубая отбраковка перед попаданием
  в очередь: служебный JSON вместо текста, запрещённые обороты школьного реферата,
  в РЕЛИЗЕ и ВЕРДИКТЕ — опись и выдуманные звук, счёт релизов и прошлое (сверка
  с данными поста). Цель — отсечь брак и перегенерировать, а не оценивать стиль.
  Брак описи и пост длиннее подписи к фото (`quality.CAPTION_LIMIT`, 1024 знака)
  после трёх попыток прощаются, выдумка — нет: такой пост пропадает.
  Чужая цитата сверяется с `outside` слово в слово; не сумела процитировать —
  чужой голос снимается с задания, и пост дописывается на своих данных.
- **[src/publish.py](src/publish.py)** — в канал публикуется только через `publish.to_channel`
  (расписание, кнопка «✅ В канал», срочные новости). Вышедший пост хранит в `content/archive`
  поле `message` — сообщение с его текстом, и по нему автопилот точности правит пост
  прямо в канале. Правка без `reply_markup` снимает кнопки, поэтому они хранятся там же.
- **[prompts/voice.md](prompts/voice.md)** — самый важный файл продукта, тон канала;
  правила отдельных рубрик — в `prompts/rubrics/*.md`, тон бота — в `prompts/service/`.

### Правила, которые нельзя нарушать

- **Канал не описываем жанрами.** ПЛЁНКА — музыкальный канал с голосом владельца.
  «Тёмный звук», «фонк, эмо-рэп, дрейн» и любые списки жанров не пишем ни в описании
  канала и бота, ни в роликах, рассылках, визитках и документах (владелец, 16.09.2026).
  Жанр остаётся там, где речь о конкретной музыке: в посте о релизе, в данных.

- **Лицо канала — плёнка, а не человек.** Нарисованную ведущую убрали:
  одинаковое синтетическое лицо из ролика в ролик площадки метят как машинный
  контент, и в январе 2026-го канал за это снесли с YouTube. Узнавание держат
  аватар канала — крутящееся колесо плеера (`assets/avatar/avatar-wheel.mp4`, он же в концовке роликов) — и обложки (`src/make_cover.py`)
  и единая камкордерная обработка кадра. Вещь нельзя обвинить в том,
  что она сгенерирована. Голос персонажа пережил и остался один на все ролики.
  Для роликов с живым голосом (`src/reels.py`) владелец 14.09.2026 решил иначе:
  камкордерной обработки и затемнения там нет, картинка чистая, на весь экран
  и всегда вертикальная (кадр обрезается под 9:16 вокруг `focus`), а марки канала
  в кадре нет вовсе — крутящуюся плёнку из угла убрали, узнаёт ролик голос.
  Клипы `src/clips.py` остаются в камкордерной обработке.
- **Ничего не выдумывать.** Модель альбом не слушала, поэтому «мрачные биты
  и атмосферные сэмплы» — выдумка, которую ловят на первом прослушивании. В посте
  только то, что проверяется по данным: треклист, длительности, гости, жанр магазина.
  Прошлое артиста — только из `previous_releases`: это найденное каналом с августа 2026
  и сверенное с магазином, а не дискография, поэтому прошлые релизы называют
  по именам и не считают.
- **О самой музыке в посте говорит только чужой голос.** Мнение издания
  (новости The Flow и RAP.RU из сбора) и отзыв слушателя под клипом на YouTube
  приходят в данные полем `outside` (`compose.outside_voice`) — это единственное
  законное суждение о звуке: канал релиз не слушал, а они слушали. Цитируется
  дословно и с именем того, кто сказал: пересказ чужого мнения — та же выдумка,
  только с чужой подписью. Новость должна называть и артиста, и релиз, иначе
  это разговор о чём-то другом. Ссылку на t.me издания в пост не ставим.
- **`data/lineage.json` и `data/subtext.json` пополняются вручную** и это сделано
  намеренно: легальных источников для текстов песен и сведений о сэмплах нет,
  а придуманный год убивает доверие быстрее всего.
- **`data/facts.json` — база клипов «А ВЫ ЗНАЛИ», и у каждой записи есть `sources`.**
  Факты сюда ищутся по источникам и проверяются, а не сочиняются: в ролике их
  читают вслух, и первое же выдуманное утверждение стоит дороже десяти
  пропущенных. Поле `artist` пишется ровно так, как имя стоит в
  `data/artists.json`, — по нему ищется фотография, и «Три 6 Мафия» вместо
  «Three 6 Mafia» оставит кадр без лица. Модели разрешено пользоваться
  только фактами из этих файлов; Last.fm добирает недостающее, но с меньшим весом —
  теги проставили слушатели, и «стоят рядом» ≠ «один вырос из другого».
- **Данные о людях не попадают в этот репозиторий никогда.** Репозиторий открытый,
  списки слежения живут в приватном `plenka-state` через `STATE_DIR`
  (см. `config.PRIVATE`), локально — в `data/private/`, которую не берёт git.
  Шифровать адреса в открытом файле бессмысленно: ключ лежал бы рядом с замком.
- **У бота один общий offset в `getUpdates`** — поэтому поллер ровно один
  ([src/moderate.py](src/moderate.py)), и разборы сервиса разбираются там же, как и голоса СЛЕПОЙ ПРОСЛУШКИ
  (`poll_answer`).
  Второй независимый опросчик воровал бы события у первого.
- **У каждого поста есть картинка.** Пост без медиа в ленте проматывают — на этом
  держится референс канала, который владелец прислал 12.09.2026. У релиза кадром
  работает обложка, у разбора (ОТКУДА НОГИ, МЕЖДУ СТРОК) — фотография артиста,
  найденного в тексте поста: `card.cover` ищет её через `footage.artist_image`,
  тем же поиском, что и клипы; разбор, не назвавший никого, берёт артиста связи
  (`compose` кладёт его в поле `artist`, где имени нет в самой связи — поле `artist`
  в `lineage.json`). Не нашли артиста или подпись длиннее 1024 знаков —
  пост уходит текстом, это запасной путь, а не норма. У новости кадром работает
  картинка издания: `feeds._entry_image` берёт её из ленты, а когда лента её
  не отдала (свой тег `<image>` у «Интермедиа» feedparser не видит) —
  `feeds.page_image` со страницы по `og:image`. Дежурный логотип издания
  за иллюстрацию не считается (`feeds.GENERIC_IMAGE`): серая плитка под новостью
  хуже текста. Своей картинки у новости быть не может — рисовать иллюстрацию
  к чужому событию значит выдумывать.
  Одно фото в канале дважды не выходит (владелец, 17.09.2026): отпечатки
  вышедших лежат в `data/posted.json` полем `photos`, и кадр, похожий на вышедший,
  уступает следующему — обложка фото артиста, портрет обложкам его альбомов
  (`card.cover`), а совместный релиз — каждому участнику. Мутный запасной кадр
  (растянутая обложка Deezer) уступает так же (`card.MIN_SHARPNESS`). Всё уже
  выходило — пост идёт текстом.
- **Под постом нет ни кнопок, ни плеера — пост всегда одна плитка ленты**
  (решение владельца от 12.09.2026). Площадки уходят ссылками в самом тексте
  (`publish.listen`): у поста канала с инлайн-кнопками Telegram не показывает
  комментарии (bugs.telegram.org/c/41803), а панель из восьми штук читалась
  раньше поста. Полный трек от владельца идёт первым комментарием под постом
  (`comments.seed`), отрывок магазина в ленту не идёт вовсе — вид поста не должен
  зависеть от того, прислали трек к релизу или нет. Перед этим комментарием
  дежурство подтягивает состояние из git: пост вышел секундами раньше.
  Трек есть — под площадками строка «▸ Или в комментариях ↓»
  (`publish.track_note`, владелец 17.09.2026): из ленты комментарий не видно,
  и за треком туда не заходят. Ставит её код, а не модель — модель не знает, будет ли трек.
  Трека к выходу нет (Mac владельца спит) — вопроса под релизом тоже нет, пост запоминает
  ветку полем `thread`, и трек, пришедший за двое суток, встаёт туда первым, а пост
  получает ту же строку (`moderate.attach_track`, владелец 18.09.2026).

## Работа с GitHub Actions

Все воркфлоу в `.github/workflows/` коммитят изменённое состояние обратно в репозиторий.
Отсюда два обязательных приёма, которые нужно повторять в любом новом воркфлоу,
пишущем в `data/` или `content/`:

- `concurrency: group: state-write` — два одновременных запуска подрались бы при коммите;
- `git pull --rebase --autostash origin ${{ github.ref_name }}` перед `git push` —
  между checkout и push мог пройти другой воркфлоу;
- `actions/checkout` с `ref: ${{ github.ref_name }}` — без него запуск берёт коммит,
  на котором встал в очередь, а не свежий. 17.09.2026 срочные новости ждали сбор
  шесть минут, упали на конфликте в `data/seen.json`, и вышедший пост остался без записи.

Ожидающий запуск в группе `state-write` GitHub вытесняет следующим. Для `review.yml`
это потерянные правки, поэтому он раз в три часа сам перезапускает ветки `claude/review-*`
старше часа, а о любой своей поломке пишет владельцу одну строку.

Журналы `data/*.jsonl` объявлены `merge=union` в [.gitattributes](.gitattributes):
локальный запуск иначе конфликтует с автоматическим.

`PUBLISH_TARGET` (Actions → Variables) переключает `admin` ↔ `channel`: пока `admin`,
посты уходят владельцу в личку с кнопками «✅ В канал» / «🗑 Удалить».

## Стиль

- **Докстринг модуля объясняет решение, а не перечисляет функции.** Принятый в проекте
  формат: чем модуль занят, почему сделан именно так, какая альтернатива отвергнута
  и почему, ниже — примеры запуска. Смотри [src/clips.py](src/clips.py),
  [src/footage.py](src/footage.py), [src/vk.py](src/vk.py) как образцы. Комментарии
  в коде — тоже про «почему», ограничения площадок описываются прямо на месте.
- **Сообщения коммитов — по-русски.** Авторские: обычная фраза о смысле изменения
  («Дежурство вместо крона: бот отвечает за секунды»), без conventional-commits
  и англоязычных префиксов. Автоматические, от `plenka-bot`: «область: что сделано»
  («сбор: новые находки»).
- Python 3.12 в CI (локально 3.14), `from __future__ import annotations` в каждом
  модуле, CLI на argparse с русскими `help`, зависимостей минимум — семь пакетов
  в [requirements.txt](requirements.txt), и список стоит держать таким.
- Вторая площадка не должна мешать основной: ВКонтакте включается сам при наличии
  токена и молча пропускается без него, а ошибка кросспостинга не роняет запуск —
  пост в Telegram к тому моменту уже вышел. Музыку туда не приложить никак:
  `wall.post` отказывает и треку, и плейлисту, поэтому подборка сообщества
  (`VK_PLAYLIST`) уходит ссылкой в тексте, а вложением — только обложка.
