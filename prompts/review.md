# Разбор выдумок: бриф автопилота

Этот файл читает облачный Claude, которого раз в два часа запускает расписание.
Как правка доходит до очереди — в докстринге [src/review.py](../src/review.py).
Здесь — что проверять, с чем сверять и как оформить правку.

Работы в каждом запуске три, и друг от друга они не зависят: разбор постов
(§1–5), мнения о свежих релизах (§6) и новые связи для ОТКУДА НОГИ (§7 — чаще
всего искать нечего, и это одна команда). Все кладутся в один файл правок (§8).

Посты пишет GigaChat, и он выдумывает. Владелец посты сам не проверяет: всё, что
ты пропустишь, выйдет в канал. Всё, что ты испортишь, — тоже. Поэтому правка
минимальная, а сомнение толкуется в пользу поста.

## 1. Есть ли что проверять

Сначала — не читая ни одного поста:

```bash
[ "$(git rev-parse --is-shallow-repository)" = true ] && git fetch -q --shallow-since="3 days ago" origin main
base=$(git rev-list -1 --before="6 hours ago" HEAD)
git diff --no-renames --diff-filter=AM --name-only "$base" HEAD \
    -- content/queue content/archive \
  | while read -r f; do
      [ -f "$f" ] || continue
      case "$f" in content/archive/*) grep -q '"message": {' "$f" || continue ;; esac
      grep -Eq '"rubric": "(pamyatka|sovet|beat|week|doposle|otbor)"' "$f" && continue
      echo "$f"
    done
```

**Пусто — разбор постов закончен**: ни одного поста не читай и переходи
сразу к §6. Так проходит большинство запусков, и это бережёт лимиты подписки.

Команду не упрощай до `git log --since`: копия репозитория у тебя неполная,
и самый ранний скачанный коммит git показывает добавившим все файлы разом.
13.09.2026 так каждый ночной проход читал все 32 поста вместо двух новых
и по второму разу правил уже исправленные.

Не пусто — это посты, добавленные, поменянные или опубликованные за шесть
часов. Окно втрое шире расписания намеренно: запуск может опоздать, а может
и не состояться вовсе (лимиты подписки), и пропущенные им посты иначе
не проверит уже никто — они выйдут в канал. По той же причине здесь нет
`--author=plenka-bot`: посты правят и руками, а 12.09.2026 именно такая
правка ушла в канал непроверенной.
Поэтому в список попадут и посты, которые прошлый проход уже видел или
исправил: проверь их так же — выдумок в них не будет, и пушить будет нечего.
Исправленный пост не шлифуй: «эмо начала нулевых» → «эмо нулевых» — не правка.

`content/queue/` — очередь. `content/archive/` — посты, **уже вышедшие
в канал**: правка уходит прямо в сообщение канала, поэтому для них только
`rewrite`, снять вышедший нельзя. Мем из архива не трогай вовсе — мем только
снимают. Вышедшие без записанного сообщения (поле `message`) список отсеял
сам: их поправить не с чем. Так же отсеяны посты, собранные шаблоном без модели
(`rubric`: `pamyatka`, `sovet`, `beat`, `week`, `doposle`, `otbor`): выдумать
в них нечего, а в ПАМЯТКЕ цитаты закона стоят слово в слово, и правка их
переписала бы. Такой пост не читай и не правь — `--check` правку не примет.
`--no-renames` не убирай: без него переезд поста
из очереди в архив git считает переименованием, и вышедший пост в список
не попадёт.

## 2. Где данные поста

Модель писала пост по определённым данным. Всё, что в посте сверх них, —
кандидат в выдумки.

| `rubric` поста | Данные | Как найти |
|---|---|---|
| `release`, `verdict` | строка `data/inbox.jsonl` | `url` строки равен `source_url` поста. Ищи по номеру альбома из хвоста адреса: `grep -F '6807382817' data/inbox.jsonl` |
| `lineage` | запись `links[]` в `data/lineage.json` | по именам и жанрам из текста: `source_url` у поста пустой |
| `subtext` | запись `items[]` в `data/subtext.json` | по артисту и треку; цитаты песен — только из `lines` |
| `legend` | запись `events[]` в `data/calendar.json` | по имени; файл поста начинается с `0000-` |
| `meme`, `poll` | только имена из `data/artists.json` | — |
| `pamyatka`, `sovet`, `beat`, `week`, `doposle`, `otbor` | собраны шаблоном, модель их не писала | не проверяются и не правятся |

**Строку inbox ищи по адресу, а не по имени.** В посте `artist` — подпись
магазина («Smoky Mo», «nkeeei & Yanix»), в inbox — имя из базы («Смоки Мо»,
«Yanix»). Подпись магазина модель получила, так что имена из поля `artist`
поста выдумкой не считаются.

Что есть в строке релиза: `artist`; `title` (« - Single» в конце — сингл);
`track_count`; `tracks` — название и `seconds` каждого трека; `duration_sec`;
`genre` — жанр по версии магазина; `tags` — метки сцены из `data/artists.json`
(`haunted-mound` подтверждает «из орбиты Haunted Mound»); `released_at`.
Гости — только те, что стоят в названиях треков после feat., ft. или with.

**Прошлое артиста проверяется по другим строкам inbox с тем же `artist`.**
«До него за лето вышли От Отца, Долги и PYREX» у Смоки Мо подтверждают три
строки его летних синглов. Таких строк нет — прошлого артиста в данных нет.

`data/facts.json` — факты с источниками. Утверждение про артиста, которое там
есть, выдумкой не считай, даже если модель этот файл не получала.

Данных поста не нашёл совсем — **пост не трогай**: без них выдумку от факта
не отличить.

## 3. Что выдумка

Фактическое утверждение, которого нет в данных поста. Правда ли это в жизни —
неважно: модель этого не знала, значит, угадала.

- **Звучание и устройство трека**: ритм, бит, бас, сэмплы, гитары, вокал, темп,
  продюсер. «Жёсткий ритм, отрывистый вокал», «рок-баллады с женским вокалом».
- **Содержание песни**: о чём поётся и какое оно. «Тепло и искренне», «без
  пафоса и драм», «простое признание» — трек никто не слушал, и оценочная
  обёртка описание не спасает.
- **Мотивы и намерения людей**: зачем релиз записан, чего артист хотел,
  что чувствовал. «Одному нужна была песня с названием покруче, другому —
  повод напомнить о себе», «решил доказать», «устал от гостей». Шутливая
  форма не спасает: это утверждение о живом человеке, и проверить его нечем.
- **Собственное прослушивание**: «я поставил фоном, а на 3-м круге заметил,
  что ни разу не перемотал», «дослушал до конца», «второй раз не стал»,
  «не снимаю с повтора». Пост писала модель, которая трек не включала, —
  это выдумка того же сорта, что «мрачные биты». Вопрос читателю
  («а ты когда последний раз дослушивал альбом до конца?») законен:
  он ни о чьём прослушивании не утверждает.
- **Прошлое артиста без строк inbox**: «после серии больших альбомов», «первый
  релиз», «долгое молчание», «вернулся». Здесь строже, чем в
  [voice.md](voice.md): там прошлое артиста разрешено «и без данных», но
  решение владельца от 11.09.2026 — это выдумка.
- **Устройство релиза сверх треклиста**: «три интерлюдии подряд», когда
  в названиях их нет; названия треков, число треков, гости.
- **Длительность в РЕЛИЗЕ и ВЕРДИКТЕ** — любая: минуты и секунды, «короткий
  трек», шутка про хронометраж (владелец, 29.09.2026: читается притянуто).
  Вырезай её, даже если цифра сходится с inbox. Не трогай только слова
  издания или слушателя в «ёлочках» — это `outside`, о длине сказал он сам.
- **Имена, лейблы, города, даты и цифры сверх данных**: «московский лейбл
  Moroz», когда в новости просто «лейбл Moroz».
- **Сцена и её обычаи**: «карельские группы обычно играют металл», «в Haunted
  Mound сингл давно главная форма высказывания».
- **Оценка самой музыки**: «лучший саундтрек десятилетия», «сильнейший альбом
  года». Канал её не слышал, судить о звуке вправе только чужой голос — поле
  `outside`, дословно и с именем. Это не «мнение» из §4: 18.09.2026 такая фраза
  вышла в канал цитатой, и проход её пропустил.

**Опечатки правь тоже**, хоть это и не выдумка: «ЗАПИШАЛСЯ НА САУНДРЕК»
18.09.2026 ушло в канал заголовком, а проход поправил в том же посте цифры
и слово оставил. Исправь только слово, остальное — буква в букву; в `fragment` —
слово с опечаткой. Выбор слов и стиль — не опечатка, их не трогай.

Правила точности канала — разделы «Красная черта» и «Правило точности»
в [voice.md](voice.md).

## 4. Что не выдумка

- **Мнение и шутка без фактического утверждения**: «Sorry Mama — это уже
  не извинение, а рубрика». Отношение
  канала к релизу — голос, а не описание музыки. Но как только в шутке
  появляется само прослушивание («дослушал», «на третьем круге») или чужой
  мотив («повод напомнить о себе»), это выдумка из §3: 12.09.2026 обе такие
  шутки автопилот принял за реакцию рассказчика, и обе вышли в канал.
- **Вывод из данных**: «никого не позвал», если в названиях треков нет feat.
- **Обобщение до десятилетия**, если оно не спорит с данными: «в нулевых»,
  «эмо-рэп 2010-х». voice.md его разрешает.
- **Одно имя в двух написаниях**: «Смоки Мо» и «Smoky Mo».
- Кнопка «▸ Слушать в …» и её адрес.

Сомневаешься, факт это или мнение, — **не трогай**. Лишняя правка портит годный
пост, и никто её не заметит.

## 5. Как править

Одна правка на пост — все его выдумки сразу.

**rewrite** — пост остаётся, выдумка уходит. Правка минимальная:

- вырежи фразу с выдумкой или замени её фактом из данных; остальной текст —
  буква в букву;
- заголовок остаётся первой строкой `<b>КАПСОМ</b>`; выдумка в заголовке —
  перепиши его по данным: кто и что выпустил;
- `<blockquote>` не удаляй; выдумка в цитате — замени её одной фразой
  отношения без фактов о музыке и без прослушивания: «дослушал», «переслушал»,
  «на повтор», «второй раз не стал» — тоже выдумка, пост писала модель, которая
  трек не слышала. Готовые реплики из образцов voice.md и рубрик не бери:
  11.09.2026 так в вердикт попало «Дослушал до конца. Второй раз не стал.»;
- строку `▸ <a href="…">…</a>` оставь символ в символ;
- в РЕЛИЗ и ВЕРДИКТ не добавляй число треков и гостей: это опись,
  её оттуда убрали; длительность не добавляй никуда и никак;
- у вышедшего поста новый текст не длиннее старого: там он подпись под фото,
  а длиннее 1024 знаков подпись Telegram не примет;
- нового не добавляй — ни фактов «для полноты», ни шуток, ни эмодзи. Тон —
  [voice.md](voice.md), запрещённые обороты оттуда проверка забракует.

**drop** — снять пост из очереди. Когда без выдумок от поста остаются заголовок,
строка «у такого-то вышел такой-то релиз» и кнопка: весь текст держался на выдумках.
ВЕРДИКТ без единого довода из данных тоже снимай — вердикт без обоснования
просто грубость (rubrics/verdict.md). Мем и опрос не переписываются,
а только снимаются: подпись мема держится на картинке, опрос — это JSON.
Вышедший пост не снимается — только `rewrite`.

## 6. Мнения о свежих релизах

Делай в каждом запуске, даже когда постов на проверку не было.

Канал релизы не слушает, и о самой музыке в посте говорит только чужой голос —
дословная цитата критика или слушателя с именем того, кто сказал. Сингл без
него поста не получает вовсе. Ты ищешь такие цитаты, а код потом сам скачает
страницу и примет цитату, только если она стоит в тексте слово в слово
([src/sources/web_voice.py](../src/sources/web_voice.py)). Пересказ или цитата
по памяти не пройдут — это потраченный впустую поиск.

```bash
python3 -m src.review --voices
```

Строка JSON на релиз, не больше пяти: `artist`, `release` и `names` — другие
написания артиста. **Пусто — мнений не ищи.**

На каждый релиз:

1. **WebSearch** рецензий и обсуждений: `"<artist>" "<release>" review`,
   reddit, Album of the Year, Rate Your Music; для русскоязычного артиста
   сначала русская пресса и слушатели — `<артист> <релиз> рецензия`, `отзыв`.
2. **Открой страницу**: `curl -sL "<url>"`, если в песочнице есть сеть, иначе
   WebFetch. WebFetch пересказывает страницу моделью — проси у него «приведи
   дословно, символ в символ, предложения о релизе» и ни слова не правь.
3. **Цитата** — 1–2 предложения, 30–300 знаков, на языке страницы, без перевода
   и без сокращений внутри: суждение о самом релизе или его звуке — похвала,
   разнос, сравнение.

Не годится — код не примет или это не мнение:

- строка песни (Genius, сайты текстов), описание в магазине (Apple Music,
  Spotify, Deezer, Яндекс, VK Музыка), пресс-релиз, новость «вышел сингл»;
- мнение об артисте вообще или о другом его релизе;
- Telegram и YouTube: у них свои пути;
- страница не о релизе: название релиза должно стоять в самой цитате или
  в заголовке страницы рядом с именем артиста;
- брань и ссылки в цитате.

`by`: `critic` — текст редакции издания, `listener` — слушатель (Reddit, RYM,
AOTY, комментарии под рецензией, форумы). Сомневаешься — `listener`: слова
комментатора, приписанные изданию, — неправда.

До трёх находок на релиз: код возьмёт первую подтвердившуюся. **Не нашёл
ничего — всё равно запиши релиз** с пустыми `url` и `quote`: код запомнит
промах, и двенадцать часов этот релиз искать не будут.

В файл правок — полем `voices` рядом с `edits`; `artist` и `release` буква
в букву из вывода `--voices`:

```json
{
  "voices": [
    {"artist": "Buckshot & Ghost Mountain", "release": "Winchester",
     "url": "https://…", "quote": "…", "by": "critic"},
    {"artist": "Lil Darkie", "release": "i love you", "url": "", "quote": ""}
  ]
}
```

Выдумок в постах нет, а мнения искал — файл с одними `voices`, без `edits`.

## 7. Новые связи для ОТКУДА НОГИ

Рубрика рассказывает, откуда вырос звук: корень → наследник. Связь рассказывается
один раз, и когда нерассказанные кончаются, базу [data/lineage.json](../data/lineage.json)
пополняешь ты. Выдумать связь нельзя: каждое утверждение идёт с адресом страницы
и дословной цитатой, и берёт запись код, а не ты.

```bash
python3 -m src.review --lineage
```

**Пусто — связей не ищи, поле `lineage` в файл не пиши.** Так проходит почти
каждый запуск: связь нужна, только когда нерассказанных меньше двух, не больше
двух в неделю и не чаще раза в сутки.

Не пусто — одна строка JSON: `need` — сколько связей нужно (1–2), `sites` — сайты,
которым код верит (Википедия на любом языке и издания сбора), `taken` — артисты,
о которых связь уже есть, `told` — уже рассказанные связи.

Что искать. Двух артистов из мира канала — рэп, тяжёлая и тёмная гитарная музыка,
русская сцена, — между которыми есть **задокументированная** связь одного из видов
(поле `kind`):

| `kind` | Что это | Что должно стоять в цитате |
|---|---|---|
| `sample` | трек наследника построен на сэмпле трека корня | кто чей трек засэмплировал |
| `cover` | наследник записал кавер | кто чью песню перепел |
| `said` | наследник сам назвал корень своим влиянием | его слова или прямое «назвал влиянием» |
| `producer` | у обоих один продюсер | продюсер и оба артиста |
| `group` | оба из одного объединения, или один вышел из группы другого | объединение и оба артиста |

**Не связь** — и не ищи под неё цитату: «звучит похоже», общий жанр, общая сцена
или город, «критики сравнивают», совместный трек или тур, твоё знание из головы,
которого нет на странице. Не бери артиста из `taken` — ни корнем, ни наследником,
даже в паре с новым: код такую запись отбросит. И не бери тему из `told`
под другими именами: седьмой пост про Мемфис и кассеты читается как повтор.

На каждую связь:

1. **Страница** — только с сайта из `sites`. Открой её сам: `curl -sL "<url>"`,
   WebFetch — если сети нет, и тогда проси «приведи дословно, символ в символ».
2. **Цитата** — 30–400 знаков подряд со страницы, на её языке, без перевода,
   пропусков и многоточий. Сноски вида `[12]` и ссылки внутри фразы не мешают:
   код сверяет слова и их порядок. Хотя бы одна цитата должна называть **обоих**
   артистов — в самой цитате или один в цитате, а второй в заголовке страницы
   (страница Википедии об одном, где сказано про другого, годится).
3. **Имена** — как у артиста в Deezer, буква в букву; так же имя должно стоять
   в цитате или заголовке. Русского артиста ищи на русских страницах.
4. **Треки** — по одному на каждый конец, со ссылкой `https://www.deezer.com/track/<id>`:
   найди через `https://api.deezer.com/search?q=artist:"…" track:"…"` и проверь, что
   `artist.name` и `title` те самые — оригинал, не концертная запись, не ремикс
   и не инструментал. Для `sample` и `cover` — те два трека, о которых цитата.
5. **Факты** — от одного до четырёх коротких русских фраз, каждая — пересказ своей
   цитаты и ничего сверх неё. **Годы и числа — только те, что стоят в цитате**:
   код сверяет цифры. Нет в цитате года — пиши без года.
6. `ancestor` — корень, `modern` — наследник (имя, можно с парой слов: «Molchat Doma
   и минский пост-панк»), `connection` — в чём связь, одной фразой без чисел
   и без оценок звука: канал музыку не слушал.

`ends` — ровно два: сначала корень, потом наследник.

```json
{
  "lineage": [
    {
      "kind": "said",
      "ancestor": "…", "modern": "…",
      "connection": "…",
      "ends": [
        {"artist": "…", "track": "…", "url": "https://www.deezer.com/track/…"},
        {"artist": "…", "track": "…", "url": "https://www.deezer.com/track/…"}
      ],
      "facts": [
        {"text": "…", "sources": [{"url": "https://en.wikipedia.org/wiki/…", "quote": "…"}]}
      ]
    }
  ]
}
```

**Искал и не нашёл ничего надёжного — `"lineage": []`.** Это норма, а не провал:
код запомнит проход, и сутки связь искать не будут. Слабую связь не дотягивай:
пустой список лучше записи, которую отбросит код или, хуже, которая пройдёт
и окажется натяжкой. На поиск — не больше получаса и не больше `need` связей.

Код при применении сам скачает каждую страницу, найдёт на ней цитату слово в слово,
сверит оба трека с Deezer и проверит, что артистов ещё нет в базе. Не прошла —
запись молча отбрасывается. Ручные связи в `data/lineage.json` не трогай и сам
файл не правь: только поле `lineage` в файле правок.

## 8. Файл правок

`content/review/<ГГГГММДД-ЧЧММ>.json`, время запуска по UTC:
`date -u +%Y%m%d-%H%M`.

```json
{
  "edits": [
    {
      "file": "content/queue/20260911-163739-1444-verdict.json",
      "action": "rewrite",
      "text": "<b>NKEEEI И YANIX ВЫПУСТИЛИ СИНГЛ ПОЦЕЛУИ</b>\n\nУ nkeeei и Yanix вышел сингл <i>Поцелуи</i>.\n\n<blockquote>…</blockquote>\n\n▸ <a href=\"https://music.apple.com/…\">Слушать в Apple Music</a>",
      "fragment": "Получилось тепло и искренне. Без пафоса и драм.",
      "why": "содержание трека: в строке inbox с этим url только название «Поцелуи», 2:05 и жанр Hip-Hop/Rap; «признание» и «без драмы» — оттуда же"
    },
    {
      "file": "content/queue/20260912-061503-4411-release.json",
      "action": "drop",
      "fragment": "…",
      "why": "…"
    }
  ]
}
```

| Поле | Что это |
|---|---|
| `file` | путь поста от корня репозитория: `content/queue/…` или `content/archive/…` |
| `action` | `rewrite` — переписать, `drop` — снять из очереди (у вышедшего — только `rewrite`) |
| `text` | только у `rewrite`: новый **полный** текст поста, а не кусок |
| `fragment` | дословная цитата самой явной выдумки из старого текста, без многоточий и сокращений; разметку можно опустить. Остальные выдумки поста — в `why` |
| `why` | чего нет в данных и где смотрел: файл, строка, поле |

Собирай файл скриптом (`json.dump` в Python), а не руками: в тексте поста
кавычки, переносы строк и HTML.

Выдумок нет ни в одном посте, мнений и связей не искал — файла нет и пушить
нечего. Заканчивай.

## 9. Проверить и отправить

```bash
python3 -m src.review --check content/review/20260912-0835.json
```

Проверке не нужны ни сеть, ни пакеты: форма файла, цитата есть в посте
и ушла из нового текста, новый текст проходит отбраковку
[src/quality.py](../src/quality.py), кнопка на месте, у мнений — форма,
у связей — форма, сайт из списка и числа из цитат.
Строка «! связь …» — применение её пропустит: убери такую запись из файла.
Строка «! … нет в списке --voices» — опечатка в artist или release: перепиши
их из вывода `--voices`. Не годен — исправь
и проверь снова; правку, которую починить не выходит, убери из файла.

Годен — ветка от текущего main, коммит одного файла, пуш:

```bash
git checkout -b claude/review-20260912-0835
git add content/review/20260912-0835.json
git commit -m "Разбор 20260912-0835: правок 2, мнений 1, связей 0"
git push origin claude/review-20260912-0835
```

**В main не пушить и ничего, кроме файла правок, не менять** — ни посты,
ни данные. Дальше само: воркфлоу «Разбор выдумок» проверит файл ещё раз,
применит правки к свежему main — вышедший пост поправит прямо в канале,
цитату и связь сверит со страницей — и удалит ветку. Пост, который за это время поменялся, он пропустит,
а вышедший поправит в канале.
